# Villacarmen backend — full MySQL → PostgreSQL migration plan

Scope: **the entire business MySQL database** (253 InnoDB tables, 23,878 rows, 1 view) plus the already-verified SQLite bot context. It all moves to PostgreSQL 17 on the local desktop only.

This is a plan only. No application code or data was changed for it, no production access was made, and nothing was sent. The earlier "keep business MySQL" boundary is withdrawn. The botstore MySQL subset work (5 tables) is preparation only. It will be **absorbed** by the full migration from the fresh 13:35 snapshot and will not be imported separately.

### 1.3 Evidence-backed obstacles

- **O1 Case- and accent-insensitive collation.** `utf8mb4_unicode_ci` makes `=`, `LIKE`, `UNIQUE`, `GROUP BY` and `ORDER BY` case- and accent-insensitive, with PAD SPACE. PG17 nondeterministic ICU collations support `=` and `UNIQUE` but **not LIKE**; LIKE support arrives in PG18. `citext` is case-insensitive only, not accent-insensitive.
  - Plan: inventory which _ci columns are used in UNIQUE keys or in equality/LIKE lookups (emails, slugs, names, phone, search).
  - UNIQUE or equality columns: a nondeterministic ICU collation `und-u-ks-level1` (accent- and case-insensitive).
  - Search/LIKE columns: the default collation plus `ILIKE`, or `unaccent(lower())` expression indexes.
  - Before applying a CI unique index, check for data that would become duplicates.
- **O2 `RowsAffected` semantics** (151 sites). Every site has to be read. Conditions like "0 means not found" stay correct, but "0 means nothing changed" or upsert "1 or 2" checks do not.
- **O3 `LastInsertId`** (145 sites) has no driver equivalent, so each one becomes `INSERT … RETURNING id`.
- **O4 Time zone.** The dump was taken with `TIME_ZONE='+00:00'`. The source `@@global.time_zone`, `system_time_zone` and `sql_mode` still need to be read by the coordinator.
  - `NOW()` on datetime columns is a wall clock in the server time zone, so PG needs the same session `timezone`.
  - timestamp columns become timestamptz in UTC.
- **O5 Strictness.** PG rejects things MySQL may currently accept:
  - non-aggregated `GROUP BY` columns, unless prod runs `ONLY_FULL_GROUP_BY`;
  - implicit text↔int comparisons;
  - `'' = 0`;
  - invalid enum values.

  These only surface per query.
- **O6 Network isolation.** The source MySQL and target PG containers are both networkless, so no single process can reach both. Transfer is file-based (export inside MySQL, `docker cp`, import inside PG) with sha256 manifests, or the coordinator mounts both sockets into one container.
- **O7 Name collision.** MySQL has its own `conversation_messages` (legacy, 6 rows, used by `conversation_history.go`). The verified SQLite-context PG store also has `conversation_messages`. The context store therefore **moves to schema `bot_context`** in the same DB (all 7 context tables, digests re-verified). Business tables keep their names in `public`.
- **O8 No SQL parser in the module cache** (no vitess or TiDB parser) and network access is restricted. A parser-based runtime translator would need a new dependency, and a regex one is rejected.
- **O9 Copied credentials inside data.** `restaurant_uazapi_instances`, `uazapi_servers`, `restaurant_ai_provider_keys`, Stripe/integration rows, SMTP and others hold live secrets. They must be copied byte-exact for verification and never be usable at runtime (see 5).

## 2. Translator vs proper port — decision

A transparent compatibility layer (a `database/sql` driver that parses MySQL SQL and emits PG SQL at runtime):
- **Can't fix:**
  - `LastInsertId`: would need RETURNING injection plus PK knowledge per statement.
  - `RowsAffected` meaning.
  - Collation semantics.
  - `VALUES()` upsert conflict targets: these need the unique-key choice per statement.
  - `GET_LOCK` session semantics.
  - Dynamic SQL (≥193 sites): built at runtime, so translation errors appear in production paths, not at build time.
- **Needs:** a full MySQL grammar (O8) and per-query semantic proof anyway.
- **Risk:** silent wrong answers (dates, counts, case folding) instead of loud failures.

**Decision: a proper port**, with a small shared dialect package and a static verification gate. No runtime SQL rewriting beyond `?` → `$n` placeholder rebinding. That rebinding is safe only because the inventory proves no `?` occurs in literals or in jsonb `?` operators.
- `internal/sqldb` provides:
  - the PG pool (pgx stdlib, `timezone` set);
  - `Rebind` and `InsertReturningID`;
  - a typed upsert helper (`ON CONFLICT (cols) DO UPDATE SET c = EXCLUDED.c`);
  - date helpers for the formats actually used (`to_char` patterns, `make_interval`, `date_trunc`, Madrid-day helpers);
  - an advisory lock on a pinned `*sql.Conn`;
  - error classification by SQLSTATE (replacing the `isSQLSchemaError` text matcher and the MySQL codes).
- Each domain's SQL is rewritten to native PG and reviewed against checklists O2–O5, in the same transaction boundaries as today (126 transactions stay transactions; no cross-DB split exists any more).
- The MySQL path is **removed** after the port; a dual-dialect codebase would double the work. Rollback is the reverse data export plus the last MySQL build tag, not runtime dual support.

## 3. Migration tooling (new static CLIs, operational, no tests)

1. **Schema translator, `dbmigrate schema`.** Reads `information_schema` of the restored source (inside the MySQL container), not the dump text. Emits PG DDL from an **explicit type map**. Anything unmapped fails closed: an unknown type, collation, expression, or a FULLTEXT/generated column without a hand mapping.
   - The 5 generated columns, 14 `json_valid` CHECKs, 2 FULLTEXT indexes and the _ci collation choices come from a reviewed mapping file.
   - Output: `pg_baseline.sql` (tables → data-free constraints → FK NOT VALID → triggers → sequences) plus a coverage report: every table, column, index, FK and CHECK listed as mapped or rejected.
2. **Export, `dbmigrate export`** (MySQL container, socket). Runs inside one `START TRANSACTION WITH CONSISTENT SNAPSHOT` and writes typed NDJSON per table plus a manifest. The manifest holds row count, AUTO_INCREMENT, per-row sha256 and a table sha256 over **canonical values**:
   - ints as decimal strings;
   - decimals at declared scale;
   - datetime at declared fsp;
   - timestamp in UTC;
   - JSON parsed and re-serialized with sorted keys;
   - blobs as hex;
   - NULL encoded separately from an empty string.

   Files are 0600, and values are never printed.
3. **Import, `dbmigrate import`** (PG container, socket). One transaction per run:
   - refuse a non-empty target;
   - `COPY` (or batched INSERT) with explicit ids;
   - re-read and canonicalize, then compare counts and every row digest against the manifest **and** the coordinator's independent row-hash snapshot;
   - `setval` every sequence;
   - `VALIDATE` all 293 FKs, where any orphan aborts with an orphan report (table, constraint, key);
   - enable triggers;
   - write the marker.

   Any mismatch or unsupported value (e.g. unsigned > 2^63-1, invalid enum, zero date) aborts the whole import.
4. **Verify / reverse export.** `dbmigrate verify` runs read-only. `dbmigrate export-pg` writes PG → manifest format, so it can be compared (and, if needed, reloaded into MySQL) for rollback. The round trip is MySQL → PG → manifest, equal to the source manifest.
5. **Context store.** `pg_dump` the 7 verified context tables, restore them into schema `bot_context` in the new DB, and re-run `botstore-migrate verify` (schema-qualified) against the source SQLite. The current context DB is kept untouched until sign-off.
6. **SQL inventory gate, `dbmigrate sqlcheck`** (static analysis plus PG as the parser).
   - `go/ast` extracts every literal or constant SQL passed to `Query/Exec/QueryRow` and lists every dynamic call site with its fragments.
   - Each static statement is **`PREPARE`d** against the empty migrated schema, which checks syntax, names, types and GROUP BY without executing anything. Dynamic sites need a recorded manual review entry.
   - The gate requires zero unprepared and zero unreviewed sites before cutover. It is an inventory tool, not a test suite.

| S3 domain ports, done in order | (a) auth/sessions/backoffice users/restaurants/config; (b) bookings, cancellations, modifications, special dates/menus, capacity, floors/tables; (c) menus/catalog/wines/stock/recipes; (d) campaigns, recipients, suppressions, `message_deliveries` outbox; (e) POS, cash days/closures, invoices, pricing, Stripe/integrations; (f) members, fichaje, schedules, compensations/payroll; (g) WhatsApp bot (absorbs the current botstore PG work), proposals/op_events; (h) analytics/AI usage/site builder/instatic/legal/ads; (i) `cmd/*` tools | **XL** (≈2,700 sites, 309 files) |

| S5 rehearsal | fresh snapshot → export → import → verify + FK report → boot PG-only server (outbound blocked) → coordinator manual QA → reverse export rollback rehearsal | M |

Order rationale: tooling and data proof first, so the schema is fixed before code. Then foundation. Then domains in dependency order, keeping each domain's transactions inside its stage. The 228 MySQL migration rows map 1:1 into `schema_migrations`, so the runner never re-applies MySQL files on PG.

## 5. No active outbound during any local run

- The code-level WhatsApp transport allowlist exists already (`WA_OUTBOUND_ALLOWLIST`). It must be kept and extended to the same pattern for **email/SMTP, Stripe/payments, LLM providers, Bunny/CDN, instatic, push, webhooks**. Every external HTTP client goes through one `outbound` guard that fails closed unless the destination is allowlisted. Only the single authorised manual WhatsApp number is allowed, and only once the coordinator starts QA.
- `BO_DISABLE_BACKGROUND_WORKERS=1` for every local run.
- The local env contains no production API keys.
- The canonical migrated DB keeps credentials byte-exact (needed for verification). QA runs against a **separate clone**, in which provider credential columns are nulled by a documented, reviewed scrub. The canonical copy is never scrubbed.
- Source MySQL: read-only, no workers, no providers.

## 6. Validation and rollback summary

- Per table: counts, per-row sha256 and table sha256 must be equal between source manifest, PG re-read and the coordinator's independent hashes. Sequences must be ≥ source AUTO_INCREMENT.
- FKs: 293 validated, orphan report empty, or the run aborts.
- CHECK, UNIQUE and generated columns are enforced on load.
- Context store: 7 tables re-verified in `bot_context`.
- Rollback: pre-cutover, drop the new DB (the source is untouched). Post-cutover, reverse export to the manifest format, reload MySQL from it, and run the last MySQL build tag. A rehearsal is required in S5.
- Fail closed throughout: any unsupported feature, mismatch or orphan stops the run and is reported. A partial success is never reported as a pass.

## 7. Trade-offs and open decisions for the coordinator

1. smallint for `tinyint(1)` (minimal code churn, chosen) vs boolean (idiomatic, ~194 columns of query and scan changes).
2. text + CHECK for enums (chosen; easy to evolve) vs native PG enums (keeps MySQL ORDER BY index semantics). Decide per column after the ORDER BY inventory.
3. Collation per column (O1): nondeterministic ICU for UNIQUE/equality vs default + ILIKE/unaccent for search. This needs the column-level inventory in S1.
4. JSON: jsonb (chosen) vs json/text where byte-exact API echo matters.
5. View `recent_conversations`: drop (chosen, broken and unused) or recreate fixed.
6. Same DB with schema `bot_context` for the context store (chosen; avoids O7) vs a separate DB (would need cross-DB transactions, so rejected).
7. The botstore MySQL-subset CLI modes are retired once the full import exists; the 5 tables come from the full snapshot.

## 8. Not done / unknown

No code was changed. No PG schema or data exists for the business DB yet. Source time zone, sql_mode and AUTO_INCREMENT values, the per-column collation usage, and the ORDER BY-on-enum inventory are still to be collected (S0/S1). The work estimate is relative; S3 dominates.
